# Operations reference

The detail behind [Deploy and operate](deploy.md), for whoever keeps an AgentCanvas installation running: what the
images and the Helm chart contain, how runs survive a redeploy, the metrics, retention and restore, and a runbook for
each alert. Install, settings, sign-in, backups, upgrades and key rotation are on [Deploy and operate](deploy.md);
every setting and its default is in [Server settings](server-settings.md).

Files named here are in the repository's [`infra/`](https://github.com/marunsct/AgentCanvas/tree/main/infra) folder:
`Dockerfile.api`, `Dockerfile.web`, `nginx.conf`, `compose.prod.yml`, `.env.prod.example`, the Helm chart
`helm/agentcanvas/`, and `docker-compose.yml` (development services only).

> Verification status (S11): both images build, and `compose.prod.yml` comes up healthy with two API replicas behind nginx on Postgres; a run streams through nginx and both replicas serve. The same checks run on the developer's machine (`make ci-full`, stage `images`: `scripts/ci-images.sh`) and in the GitHub workflow's `images` job, which runs only when started by hand (Actions → ci → Run workflow); both lint and render the Helm chart.

## The images

The build commands are in [Deploy and operate](deploy.md#option-1-docker-compose-on-one-host).

- **Frameworks in the API image:** LangGraph and the OpenAI Agents SDK always. The others (CrewAI, Google ADK, Pydantic AI, Agno, the Microsoft Agent Framework, Strands, LlamaIndex, Mastra) only when the build names them: `--build-arg FRAMEWORKS=all --build-arg WITH_MASTRA=true` (the documented commands and the Docker app), a list of ids, or nothing (the Dockerfile's default, used by CI). Workflows of a framework the image lacks can be designed and exported, but not run.
- **API image:** multi-stage (uv builds the virtualenv; the runtime stage has no build tools), runs as uid 10001, includes `git` for project workspaces, logs JSON, and exposes `/healthz` (liveness) and `/readyz` (the database and the run store answer; 503 otherwise). `ruff` is a runtime dependency: the code generator formats output with it. On SIGTERM uvicorn lets open streams finish for up to 30 s.
- **Web image:** nginx (unprivileged, port 8080) serves the built app and proxies `/api/` to `$API_UPSTREAM` (default `http://api:8000`) without buffering, so Server-Sent Events stream in real time. Hashed assets are cached for a year; the app shell is always revalidated.
- The framework environments the API image can include (`--build-arg FRAMEWORKS=...`, all of them in the Docker app) are installed from the locks in `apps/api/framework-locks/`, every package pinned with its hashes, and Mastra from its `package-lock.json`, so two builds of the same commit contain the same packages. `scripts/audit-deps.sh` checks all of them, with the API's and the web app's dependencies, for known vulnerabilities, and the image scan (Trivy, `scripts/ci-images.sh`) runs on an image built with every framework and Mastra.
- **Third-party licences and bill of materials:** the web image serves the licence of every package bundled into the app at `/third-party-licenses.txt` (minifying removes the comments that carried them). In the API image each Python package keeps the licence files it ships in its `.dist-info` folder under `/app/.venv` (and the framework environments under `/app/.frameworks`). The images check (`scripts/ci-images.sh`, or the workflow's `images` job) writes a CycloneDX SBOM of each image, every OS and language package with its licence, to `.ci-tmp/sbom/` (`SBOM_DIR` to change it; the workflow uploads them as the `sbom` artifact): keep them with each release for a customer's compliance review.
- Base images are pinned by digest in the Dockerfiles; Dependabot proposes new digests weekly. Its version updates (images, Python and npm packages, actions) wait until a release is 7 days old, 14 for a major version, so a hijacked release is usually pulled before it reaches a pull request; security updates do not wait. To build from a mirror, replace the exact reference with BuildKit: `docker build --build-context 'python:3.12-slim@sha256:<digest>=docker-image://mirror.gcr.io/library/python@sha256:<digest>' …` (same digest: the mirror serves the same image).

## What the Helm chart creates

How to install it is in [Deploy and operate](deploy.md#option-2-kubernetes-with-helm).

| Object | Notes |
|--------|-------|
| `Deployment …-api` | 2 replicas by default; startup and liveness probes on `/healthz`, readiness on `/readyz`; rolling updates never drop below the replica count; `terminationGracePeriodSeconds: 60` and a 5 s `preStop` so open streams can finish; non-root, all capabilities dropped, a read-only root filesystem with `/tmp` (1 GiB) and `/home/app` as scratch volumes (`api.readOnlyRootFilesystem: false` if a framework must write elsewhere), no Kubernetes service-account token, and `fsGroupChangePolicy: OnRootMismatch` so a start does not re-own every workspace file |
| `Deployment …-web` | nginx; 2 replicas; proxies `/api/` to the API service; read-only root filesystem (scratch volumes for `/tmp` and the rendered `/etc/nginx/conf.d`), no service-account token |
| `Job …-migrate-<revision>` | `alembic upgrade head` as a `pre-install,pre-upgrade` hook, so new API pods never start against an old schema. Migrations run one at a time however many start together. Indexes on large tables (runs, conversations) are built `CONCURRENTLY`, so the running API keeps writing while they build. Such a build waits for transactions that were already open, so on a large database the hook can take minutes; an index left unfinished by a failed run is rebuilt by the next one; read-only root filesystem, no service-account token |
| `PersistentVolumeClaim …-workspaces` | project workspaces (git) shared by every API replica: needs a **ReadWriteMany** storage class (EFS, Filestore, Azure Files, NFS); kept on uninstall |
| `Ingress` | routes everything to the web service; annotations turn proxy buffering off and allow hour-long streams |
| `NetworkPolicy …-api` | only the web pods reach the API port |
| `PodDisruptionBudget …-api`, `-web`, `-sandbox`, `-egress` | `minAvailable: 1` for each component running 2+ replicas, so a node drain or cluster upgrade never takes all of them (`podDisruptionBudget.*`); every Deployment also spreads its pods across nodes (`topologySpread.*`, `ScheduleAnyway`) |
| Secrets | never in values: name an existing Secret (`secrets.existingSecret`), for example one synced by External Secrets |

## Replicas, redeploys and running conversations

**Several replicas are safe:** runs persist in Postgres, a reconnecting client reads state via `GET /v1/threads/{id}`, so sticky sessions are not required. Each cron minute starts one run however many replicas tick: a scheduler claims the minute by moving the trigger's `last_fired` forward in a conditional update, and only the replica whose update matched starts the run.

**Safe redeploy (FR-X-10).** A rolling update never loses a run. On SIGTERM an API pod leaves the Service (`preStop`), uvicorn gives open streams 30 s, then the pod *drains*: `/readyz` answers 503 `{"status":"draining"}`, new runs get 503 with `Retry-After: 5`, and running runs get `AGENTCANVAS_DRAIN_GRACE_S` (20 s) to finish. Runs still going are stopped at their last checkpoint: they end `interrupted` with error code `redeploy` and `run.handover` set. Every replica looks for handed-over runs at startup and every `AGENTCANVAS_HANDOVER_INTERVAL_S` (10 s), claims each with a conditional update (one replica wins), and continues the conversation from its checkpoint on the version it was running. Keep 5 + 30 + drain grace below `terminationGracePeriodSeconds` (60) and compose's `stop_grace_period` (60 s). A step that was cut off runs again on the new pod, so steps with side effects should be idempotent (the same rule as retries). A pod killed without draining (OOM, a lost node) cannot hand its runs over, so each replica refreshes the heartbeat of its running runs on every hand-over tick; a run still `running` without a heartbeat for `AGENTCANVAS_ORPHAN_AFTER_S` (60 s) is marked `interrupted` and handed over the same way.

**Publishing over running conversations.** A deployment's conversations continue on its newest version only when that version can resume them: every state field keeps its type and reducer and every pause point (approval, human input, tool approval) keeps its step name and kind. Otherwise a conversation finishes on the version it started on (`run.workflow_version_id` shows which), and new conversations get the new version.

**Client addresses.** The audit log records the caller's IP from `X-Forwarded-For` only when the direct peer is a trusted proxy: set `FORWARDED_ALLOW_IPS` (uvicorn) to the proxies' addresses. The chart uses `*` (`config.forwardedAllowIps`) because only the web pods can reach the API: it adds a NetworkPolicy that admits only them (`networkPolicy.enabled`). If you turn the policy off or expose the API another way, list the proxies instead. `compose.prod.yml` and `compose.local.yml` trust only the `front` network nginx and the API share (`FORWARDED_ALLOW_IPS` = `FRONT_SUBNET`, default `10.250.251.0/24`), and publish no API port.

## Configuration details

The settings to decide first are in [Deploy and operate](deploy.md#essential-settings). Some behaviour behind them:

- **Required in production:** `AGENTCANVAS_ENV=prod`, `DATABASE_URL`, `AGENTCANVAS_SECRET_KEY` (64+ random chars), `LANGGRAPH_AES_KEY`, `AGENTCANVAS_AUTH_MODE=oidc` with `AGENTCANVAS_OIDC_ISSUER`, `AGENTCANVAS_OIDC_AUDIENCE` and `AGENTCANVAS_OIDC_CLIENT_ID`, `AGENTCANVAS_CORS_ORIGINS`. The API refuses to start in staging, prod or the hosted edition with `AUTH_MODE=dev`.
- **Sign-in tokens.** The web app uses authorization code + PKCE (post-logout URI `https://<app>/`). The API checks the access token's signature (JWKS from the issuer's discovery document, or `AGENTCANVAS_OIDC_JWKS_URL`), `iss`, `aud` and `exp`. The default scopes (`AGENTCANVAS_OIDC_SCOPES`) include `offline_access`, so the client gets a refresh token and renews the access token silently; allow refresh tokens for the client at the provider (or drop the scope to fall back to a hidden-iframe renewal, which browsers that block third-party cookies break). Optional: `AGENTCANVAS_OIDC_EMAIL_CLAIM`, `AGENTCANVAS_OIDC_TRUST_EMAIL=true` for providers that send no `email_verified` but own the email domain.
- **Database connections.** Requests give their connection back when the response starts, so open streams hold none (load test M8-T5: 200 concurrent streams on two replicas, p95 time to first event 89 ms). The pool sizes and the sum Postgres must allow are in [Deploy and operate](deploy.md#option-1-docker-compose-on-one-host).
- **First admin.** On their first verified sign-in the emails in `AGENTCANVAS_BOOTSTRAP_ADMIN_EMAILS` become admins of the default organisation (once: an admin removed later is not re-added). With sign-in on, the seeded development user loses its memberships at startup. Admins then invite everyone else from the Members page (`PUT /v1/org/members`). Roles and policies: [Organisations, roles and policies](accounts.md).
- **Long-term memory per organisation.** Runs keep memories under the workflow's organisation (namespaces start with `org:<id>`), and the Memory inspector works inside the caller's organisation. On upgrade from v0.1.0, existing memories move to the default organisation once, at the first start; the API records that and never moves memories again. Deployment API end users are kept as `api:<deployment>:<user_id>`, apart from organisation members.
- **Secrets at rest (envelope encryption).** Project secrets and webhook signing secrets are encrypted with a random data key per organisation; the data key is stored wrapped by the master key in `AGENTCANVAS_KMS_KEY`: `file:/run/secrets/master.key` (32+ random characters), `aws:<key ARN>` (install `boto3`), `gcp:<key resource name>` (install `google-cloud-kms`), or empty to derive it from `AGENTCANVAS_SECRET_KEY` (development). Rotation: [Rotating the secrets master key](deploy.md#rotating-the-secrets-master-key).
- **Checkpoints at rest.** With `LANGGRAPH_AES_KEY` set (16, 24 or 32 characters, the AES key sizes) conversation checkpoints are encrypted with AES; checkpoints written before stay readable. The API logs `checkpoints.unencrypted` at startup in staging and prod without it.
- **Browser policy.** The web image sends a Content-Security-Policy; sign-in calls the identity provider, so its origin (taken from `OIDC_ISSUER`, which compose and the chart pass from the API settings) is allowed in `connect-src`. If the token or keys endpoints live on another host, list those origins in `CSP_CONNECT_SRC` (chart: `web.cspConnectSrc`).
- **Rate limits.** nginx limits the public deployment and webhook endpoints to 20 requests/s per client address (bursts of 40, then 429). The API also limits each caller per minute, counted in the database so the limits hold across replicas (the settings are in [Deploy and operate](deploy.md#essential-settings)); `AGENTCANVAS_RATE_LIMIT_BY_ENVIRONMENT` overrides the per-key limit for a deployment environment (JSON, e.g. `{"dev": 30}`); 0 turns a limit off. Over a limit the API answers 429 with `Retry-After`.

## Observability

- **Logs:** JSON (structlog) to stdout in the images; ship with your platform's collector. Fields: `request_id`, `workflow_id`, `thread_id`, `run_id`, `level`, `event`, and `trace_id` / `span_id` inside a traced request.
- **Metrics:** Prometheus at `GET /metrics` on each API pod (`AGENTCANVAS_METRICS_ENABLED`, on by default). The web image's nginx answers 404 for `/api/metrics`, so scrape the pods directly; the Helm chart adds `prometheus.io/*` pod annotations and lets the `monitoring` namespace through its NetworkPolicy (`observability.metrics.*`).

  | Metric | Labels | Meaning |
  |---|---|---|
  | `agentcanvas_runs_started_total` | `origin` (user, trigger, event, test, api…) | runs started |
  | `agentcanvas_runs_finished_total` | `origin`, `status` (success, interrupted, error, cancelled) | runs finished or paused |
  | `agentcanvas_run_duration_seconds` | `status` | histogram of run duration |
  | `agentcanvas_runs_active` | | runs in progress in this pod |
  | `agentcanvas_tokens_total` / `agentcanvas_cost_usd_total` | `direction` | model usage and cost |
  | `agentcanvas_sse_clients` | | open run event streams |
  | `agentcanvas_http_requests_total` / `agentcanvas_http_request_duration_seconds` | `method`, `route` (template, never ids), `status` | HTTP traffic |
  | `agentcanvas_online_score_mean` | `deployment`, `evaluator` | mean online score over the evaluator's alert window (S13) |
  | `agentcanvas_eval_alert_open` | `deployment`, `evaluator`, `kind` (below, drop) | 1 while a drift alert is open; every pod refreshes it from the database once a minute |
  | `agentcanvas_eval_alerts_total` | `kind` | drift alerts opened |

- **Traces:** OpenTelemetry spans for FastAPI, the control database (SQLAlchemy) and outgoing httpx calls when `OTEL_EXPORTER_OTLP_ENDPOINT` is set (OTLP/HTTP; the standard `OTEL_*` variables configure it; Helm: `observability.otlpEndpoint`). Request spans carry `request.id`. LLM traces go to LangSmith when `LANGSMITH_TRACING=true` (runs tagged with `workflow_id`).
- **Dashboard and alerts:** `infra/observability/grafana-dashboard.json` (import it and pick the Prometheus data source) and `infra/observability/alerts.yaml`: server errors above 5 % for 10 min, more than 20 % of runs failing, API p95 above 2 s (streams excluded), no API pod scraped, and an online evaluator in drift for 5 min (`AgentCanvasEvaluationDrift`, severity ticket).
- **Online evaluation (S13).** Scoring of sampled deployment runs happens in each API pod after the response is sent (at 30 requests/s with every run scored, p95 rose from 42 to 52 ms on compose prod; lower the sampling rate for heavy traffic or LLM judges); an LLM judge's calls use the project's model keys and their cost is reported apart from run cost (the *Production* tab). LangSmith dataset sync uses the project secret `LANGSMITH_API_KEY`, else the server's environment variable of that name, and `LANGSMITH_ENDPOINT` for a self-hosted LangSmith.

## Retention, restore and disaster recovery

Backups and the keys to keep with them are in [Deploy and operate](deploy.md#backups).

- **Retention (M8-T4).** A job in every API pod deletes conversations (threads with their checkpoints, runs and decisions) that have been inactive longer than the organisation keeps them: `PUT /v1/org/settings {"retention_days": 30}` (admin; `null` = the server default `AGENTCANVAS_RETENTION_DAYS`, 90; `0` = keep forever). Conversations that are running or waiting for a person are never deleted. What a deleted conversation's runs spent (runs, tokens, cost, per workflow, deployment, person and hour) is kept, without any content, so day and month budgets and the spending report still count it; it goes when its workflow is deleted. It checks every `AGENTCANVAS_RETENTION_INTERVAL_S` (1 h) and counts deletions in `agentcanvas_threads_expired_total`. The same job deletes audit-log rows older than `AGENTCANVAS_AUDIT_RETENTION_DAYS` (400; `0` keeps them forever) and, only when `AGENTCANVAS_MEMORY_RETENTION_DAYS` is set (off by default), long-term memories (and Deep Agent store files) not updated for that many days, in every organisation. Otherwise erase memories from the Memory inspector.
- **Managed Postgres:** turn on point-in-time recovery (7 days or more). Restoring to a point in time is the provider's operation; then point `DATABASE_URL` at the restored instance and roll the API pods (the migration hook runs first).
- **Restore runbook** (an earlier version of the script was rehearsed on compose prod on 2026-10-05: a conversation deleted after the backup came back with its state; about 11 s for a small database. That was before the API got its own database role and before the workspaces archive; the current script has not been rehearsed since):
  1. `ENV_FILE=infra/.env.prod infra/scripts/restore.sh <file.dump>`. This stops `web` and `api`, recreates the database, creates the API's role (`agentcanvas_app`) before loading the dump (the dump names it as an owner and in grants, and a new server lacks it), restores the workspaces archive when it lies beside the dump, runs migrations (a backup from an older release is brought up to date; the role's grants are renewed), and starts the API and web again. Restoring into another server by hand: `pg_restore --no-owner --no-acl`, then run `alembic upgrade head` and `python -m agentcanvas.db.app_role` as the owner.
  2. Check `GET /readyz`, sign in, and open a recent conversation.
  3. Runs that were in progress when the backup was taken show as running; cancel or resume them from the Run panel.
- **Drill** quarterly: restore into a scratch environment, run the smoke checks above and record how long it took.

## Runbooks

The alert rules in `infra/observability/alerts.yaml` link here. Logs are JSON; the `event` field names what happened.

| Situation | First steps |
|-----------|-------------|
| API pods crash-loop at startup (`AgentCanvasApiDown`) | Read the last lines before the exit: `kubectl logs <pod> --previous` (compose: `docker compose -f infra/compose.prod.yml logs api`). The API refuses to start on a configuration that would be unsafe, and the error names the setting: `AUTH_MODE=dev` in staging or prod; `oidc` / `matura` without `AGENTCANVAS_OIDC_ISSUER` and `_AUDIENCE`; `AGENTCANVAS_SECRET_KEY` shorter than 32 characters or the development default; `SCRIPT_EXECUTION` `inprocess` / `subprocess` in staging or prod without `AGENTCANVAS_ALLOW_UNISOLATED_SCRIPTS`; `remote` without `AGENTCANVAS_SANDBOX_URL` and `_TOKEN`; `AGENTCANVAS_MATURA_URL` without its client secret; a malformed `AGENTCANVAS_MODEL_PRICES`; in Matura mode in staging or prod, a database role that bypasses row-level security. A pod that never becomes ready but does not exit: `/readyz` answers 503 while the database or the run store does not answer (check `DATABASE_URL`, network policy, `max_connections`). With `AGENTCANVAS_AUTO_MIGRATE=false`, check that the migration Job or service succeeded (`kubectl get jobs`, `docker compose ps -a migrate`) |
| Workspace code fails with "every sandbox was busy for 60 s" | Each sandbox pod or container runs one call at a time and a call waits up to 60 s for one (the service answers 503 `busy`). Add replicas (`sandbox.replicas` in Helm, `SANDBOX_REPLICAS` in compose); look for scripts that run close to their time limit (`sandbox.json` `timeout_s`). "the sandbox service is not reachable": the sandbox pods are not ready, or the NetworkPolicy does not admit the API pods |
| Workspace code cannot reach a host (egress refusals) | The proxy's answer says why. 403 "not in this project's sandbox.json egress list": add the host (and port, 443 by default) to the project's `sandbox.json`. 403 "private address": the name resolves to a private range, which the proxy reaches only with `AGENTCANVAS_EGRESS_ALLOW_PRIVATE=1` (never link-local or metadata addresses). 407: the call's signed list expired or `AGENTCANVAS_EGRESS_SECRET` differs between the API and the proxy. 502 "does not resolve" / "not reachable": DNS or the route out of the proxy (in Helm, `sandbox.egress.deniedCidrs` and the cluster's egress) |
| Workspace volume full | Saving files, publishing or creating projects fails with "No space left on device". Check with `kubectl exec deploy/<release>-api -- df -h /data/workspaces` (compose: `docker compose exec api df -h /data/workspaces`). Grow the PersistentVolumeClaim (`kubectl patch pvc <release>-workspaces -p '{"spec":{"resources":{"requests":{"storage":"20Gi"}}}}'`, when the storage class allows expansion; set `workspaces.persistence.size` to match) or free the host's disk under compose; then look for projects holding large files |
| Database failover (managed Postgres) | During the switch `/readyz` answers 503, so pods leave the Service and new requests wait; the control pool tests each connection before use (`pool_pre_ping`) and reconnects. Steps that were writing a checkpoint at that moment may end in an error: resume or rerun them from the Run panel. If the endpoint's address changed, update `DATABASE_URL` in the Secret and roll the API (`kubectl rollout restart deploy/<release>-api`). Afterwards check `max_connections` on the new primary |
| Rotate `AGENTCANVAS_SECRET_KEY` | Do not just replace it: with `AGENTCANVAS_KMS_KEY` empty it is the master key of every project secret, and it still decrypts secrets written before v0.3.0. Follow [Rotating `AGENTCANVAS_SECRET_KEY`](deploy.md#rotating-agentcanvas_secret_key) |
| Rotate `AGENTCANVAS_SANDBOX_TOKEN` or `AGENTCANVAS_EGRESS_SECRET` | Neither encrypts anything stored; there is one value at a time, so workspace code calls fail for the moments the API and the sandbox (or the egress proxy) disagree. Update the Secret (compose: `infra/.env.prod`), then restart both sides together: `kubectl rollout restart deploy/<release>-sandbox deploy/<release>-egress deploy/<release>-api` (compose: `docker compose -f infra/compose.prod.yml --env-file infra/.env.prod up -d`, which recreates the containers whose settings changed). Calls that failed in between can be run again |
| Nobody can sign in, every request 401 "cannot load the identity provider's signing keys" or "cannot find the token's signing key" (JWKS outage) | The API fetches the provider's discovery document and keys and keeps the key set for `AGENTCANVAS_OIDC_JWKS_CACHE_S` (1 h): a short outage goes unnoticed by pods that already have the keys, new pods and keys rotated meanwhile fail. Check the provider's `/.well-known/openid-configuration` and `jwks_uri` from an API pod (egress rules, DNS, TLS). Deployment API keys, webhooks and share links do not depend on the provider and keep working. If the discovery document is down but the keys are reachable elsewhere, set `AGENTCANVAS_OIDC_JWKS_URL` |
| Runs stuck "running" | graceful restarts hand runs over (FR-X-10, [above](#replicas-redeploys-and-running-conversations)); runs of a pod that was killed (OOM, node loss) are taken over by another pod after `AGENTCANVAS_ORPHAN_AFTER_S` (60 s) without a heartbeat (S12). If they stay `running`, check that at least one API pod is up, then cancel them from the Run panel |
| SSE shows nothing until the end | a proxy is buffering: check ingress/nginx `proxy_buffering off`, header `X-Accel-Buffering: no` |
| DB connection exhaustion | Lower the pools per replica (`AGENTCANVAS_DB_POOL_SIZE`, `_DB_MAX_OVERFLOW`, `_PERSISTENCE_POOL_SIZE`) and look for long transactions (`pg_stat_activity`). A connection pooler such as PgBouncer in front of the control database needs three things, or the API breaks: **(1)** PgBouncer 1.21 or later with `max_prepared_statements` above 0 (for example 200) in transaction pooling, because the API's driver (psycopg) prepares statements, and the run store prepares every one. **(2)** `ignore_startup_parameters = options`: PgBouncer refuses the startup option that turns on `agentcanvas.all_tenants` (row-level security lets the API's background work see every organisation only with it), so the API's role must carry that setting itself. The migration step gives it to the role (`APP_DB_USER`) when it runs as a superuser, as in the compose stack; a managed Postgres's owner is not one, and the step then prints a notice: have a superuser run `ALTER ROLE agentcanvas_app SET agentcanvas.all_tenants = 'on'`, or, with transaction pooling, add `connect_query='SET agentcanvas.all_tenants = on'` to the database's line in PgBouncer. The API refuses to start when its connections would see no rows, and says so. **(3)** Point the run store at Postgres directly (`AGENTCANVAS_PERSISTENCE_URL`, the same database without the pooler) or use session pooling for it: it holds a session lock while it upgrades its tables at startup. Then raise `max_connections` for the sum in [Deploy and operate](deploy.md#option-1-docker-compose-on-one-host) less what the pooler saves |
| Model provider outage | give the affected AI blocks **backup models** from another provider ([Models](models.md#backup-models-and-reusing-answers)), then publish again so deployments use them |
| Evaluation drift alert | open the workflow's Evaluation page → *Production*: compare the hourly mean with the 7-day trend, open the lowest-scoring runs (their timelines are one click away), and send them to an annotation queue; a recent publish or a model provider change is the usual cause. The alert resolves by itself once the window's mean recovers |
| Leaked secret | revoke the key at the provider first, then store the new value: **Project › Secrets** for a project secret, the server's environment (and a restart) for a server-wide key, **Rotate key** on the deployment's page for a deployment's API key, revoke for a personal token. Secret values are never shown again through the app or the API, and reads are not audited, so the audit log cannot tell whether a secret was used: assume it was. The audit log shows who changed secrets and keys (actions `put_secret`, `delete_secret` and `rotate_key`) and from where |
